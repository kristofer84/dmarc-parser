# Where things live

A concern → file map, with the trap that has already cost time once. Read the row before
touching the area; it is cheaper than rediscovering it.

| Concern | Where | What bites |
|---|---|---|
| **Database, schema, migrations** | `backend/prisma/schema.prisma`, `backend/prisma.config.ts`, `backend/src/db/prisma.ts` | There is no `migrations/` directory. `initializeDatabase()` runs `npx prisma db push` on **every start**, so a schema change is applied by restarting the container; a restore from an older backup is migrated forward automatically, while running an **older image against a newer database** is the case that breaks. `--accept-data-loss` is deliberately **absent** (Prisma 7): additive changes apply, a destructive one fails the start loudly instead of dropping a column. Prisma 7 specifics: the client is generated into `src/generated/prisma` (gitignored, compiled by tsc), the datasource URL lives in `prisma.config.ts` (not the schema), SQLite goes through `@prisma/adapter-better-sqlite3`, and the adapter **must** keep `timestampFormat: 'unixepoch-ms'` - existing rows store DateTime as INTEGER epoch-ms, so the default ISO-text writer would sort every new row after all of them. |
| **Unrecognised attachments** | `imapClient.ts` (`kind: 'unknown'`), `emailProcessor.processUnknownAttachment` | Anything that reaches the reports mailbox and is not rua/ruf/TLS-RPT is written to the processing log with its filename, content type and size. It used to be a console line only, which vanished with the container. |
| **Aggregate (rua) ingestion** | `backend/src/services/emailProcessor.ts`, `imapClient.ts`, `dmarcParser.ts` | The mailbox is only read (`includeRead=false` means `UNSEEN`); successfully processed UIDs are moved to the archive folder afterwards. A report with `dkim`/`spf` outside `{pass, fail}` is rejected wholesale — `temperror` and `neutral` reports are dropped, not partially stored. `reportId` is the dedup key, so re-processing is idempotent. |
| **TLS-RPT ingestion (RFC 8460)** | `services/tlsRptParser.ts`, `emailProcessor.ts`, `routes/tlsRpt.ts`, model `TlsRptReport` | JSON or gzipped JSON, classified in `imapClient.ts` *before* the DMARC check (a `.json` can never be an aggregate report). One row per policy entry: a report can cover several domains/MX hosts. Dedup is `report-id|domain|mx`, falling back to a content hash. `failure-details` is stored as JSON because that is the part that says *why* TLS failed. Reports are domain-scoped on read like everything else. |
| **Forensic (ruf) ingestion** | `rufParser.ts`, `emailProcessor.ts` | These can contain the reported message itself. Headers are always kept; `forensics.storeFullHeaders`, `storeReportedMessage` and `storeRawFeedback` are opt-in (settings). `reportAuthenticated` comes from the enclosing mail's `Authentication-Results` header — the mailbox is world-writable, so an unauthenticated report is a claim, not a fact. Dedup key is the report mail's Message-ID, else a hash of the identifying fields. |
| **Passwords & sessions** | `backend/src/services/auth.ts`, `sessionCookie.ts` | scrypt (N=16384, r=8, p=1) with a versioned format string; only the SHA-256 of the session token is stored. Changing a password destroys every session for the account **and mints a fresh one** for the caller — forget that and the user is signed out by their own password change. `lastSeenAt` is throttled to 5 minutes, so it is not a live "online" indicator. |
| **Passkeys (WebAuthn)** | `services/webauthn.ts`, `webauthnConfig.ts`, `routes/webauthn.ts` | Bound to the exact origin in `PUBLIC_ORIGIN`. Renaming the hostname — or reaching the app by IP — silently invalidates every registered passkey, with no error the UI can show. Ceremony state is single-use and consumed before verification. Counter regression is treated as a possible cloned authenticator. Passkeys are additive: passwords never go away. |
| **OIDC / single sign-on** | `services/oidc.ts`, `routes/oidc.ts` | The IdP conveys identity only; **no claim confers a role or domain**. A new account is `role: 'user'` with no domains. Linking an external identity to an existing account requires `email_verified`. The callback URL is registered per provider and is derived from `PUBLIC_ORIGIN`, so changing that origin breaks sign-in until the IdP is updated. |
| **Authorisation / per-domain scoping** | `middleware/auth.ts` (`getDomainScope`, `isDomainAllowed`), applied in `routes/reports.ts`, `summary.ts`, `forensics.ts`, `domains.ts`, `processingLogs.ts` | `null` means unrestricted (admin); `[]` means nothing assigned and must return empty results, not an error. Out-of-scope per-domain resources answer **404, not 403**, so ids cannot be probed. Any new route that reads report data must apply the scope in the query itself. |
| **Audit trail** | `services/audit.ts`, `middleware/audit.ts`, `routes/audit.ts`, model `AuditEvent` | Route handlers **never call `recordAudit` directly** — they set `req.audit = { action, target, detail }` and the middleware writes one row on `finish`, taking the outcome from the status code. Doing both double-counts. Reads are not recorded unless the route opts in (`audit.export` does); a POST that only reads sets `ignore: true` (`domain.records`). Credential-shaped detail keys are redacted at write time — never rely on that, just do not pass them. The table is append-only by application design: the only deletion is the retention prune. It is **not** tamper-evident against someone with the database file; the export's SHA-256 proves the *file* was not altered after it left the box. |
| **Retention** | `services/retention.ts`, settings `data.*`, scheduler in `index.ts`, admin endpoints in `routes/settings.ts`, UI panel in `AdminSettingsView.vue` | Three rules: aggregate reports anchored on the report period `endDate`; forensic reports on `arrivalDate` falling back to `createdAt`; audit rows on `createdAt`. `0` = keep forever. Runs 90 s after start and every 6 h, and serialises with the manual run through one in-flight promise. Deletion is irreversible and a backup taken earlier still contains the rows. Records cascade with their report; processing logs keep their rows with `reportId` set to null. |
| **DNSSEC** | `services/dnssec.ts`, `cli/dnssec.ts`, `domainStatus.ts` (`checkDnssec`), `recordSuggestions.ts` (`generateDnssec`) | Node's stub resolver cannot ask for DS or DNSKEY, so this uses DNS-over-HTTPS (Cloudflare, then Google) - the answer is therefore "a validating resolver sees X", with the AD bit passed through, not local validation. The digest (RFC 4034 §5.1.4) and key tag (Appendix B) are computed here; that is what makes "the DS at the registrar matches a key in the zone" a fact. A DS matching no key is an `error`, not a warning: it takes the whole domain off the air for validators. `npm run dnssec <domain>` prints the same inspection from the CLI, `--ds` prints just the registrar values. |
| **Domain checks** | `services/domainStatus.ts`, `domainMonitor.ts`, `routes/domains.ts` | Checks are MX/TXT/A/AAAA/CNAME/CAA only: **no PTR, no public-suffix list, no alignment computation, no DKIM selector discovery** (selectors are manual config; empty means `skipped`). `checkDmarc` reads only the first `v=DMARC1` record and does not flag duplicates. A discovered domain is added unchecked and unmonitored. |
| **Record suggestions** | `services/recordSuggestions.ts`, `POST /api/domains/:id/records` | Read-only advice; it never writes DNS. It runs a check inline when the domain has never been checked, which is why it is a POST — and why it is excluded from the audit trail (`ignore: true`). Known wart: the CAA suggestion reports `type: 'TXT'` while its own note says CAA. |
| **Runtime settings** | `services/settings.ts`, `routes/settings.ts` | Values live in the `settings` table, typed against the `SETTINGS` array, cached for 15 s (writes invalidate). Secrets are never returned by the API — only `isSet`. Add a new setting to the array and it is seeded on the next start; there is no migration to write. |
| **Frontend routes & nav** | `frontend/src/main.ts`, `frontend/src/App.vue` | No `src/router/` directory — routes are declared in `main.ts`. Navigation is derived from `isAdmin` in `App.vue`, not from a second hardcoded list: add an admin page by extending `moreNavLinks`. `meta.admin` on a route is enforced in the router guard, and `meta.title` feeds the document title. |
| **Frontend data layer** | `frontend/src/api/client.ts`, `frontend/src/types/api.ts` | One axios singleton with `withCredentials`; a 401 on anything but `/auth/*` clears the session and routes to login. Secrets in responses are absent by design, so never "fix" a blank by reading a new field. Exports/downloads return blobs and must read headers (e.g. `X-Audit-Digest`) inside the client — axios drops them otherwise. |
| **Glossary** | `frontend/src/data/glossary.ts`, `frontend/src/views/GlossaryView.vue`, `docs/dictionary.md` | Data file first, doc second. `whyItMatters` may only name things the app actually does; several entries exist to say a check does *not* exist. Anchors are the term `id` (`/glossary#dkim-selector`). |
| **Build** | `Dockerfile`, `frontend/vite.config.ts`, `backend/tsconfig.json` | The published image serves the SPA **from the API process** (`STATIC_DIR`), so there is no nginx and no CORS in the quickstart. The Dockerfile builds the frontend with `build:docker` and deliberately skips type-checking there — CI does that cheaply instead. |
| **Deployment** | `compose.quickstart.yml`, `docker-compose.yml`, `deploy/README.md` | The two compose files are different topologies (single container vs frontend+backend behind host nginx). The API trusts `X-Forwarded-For`, so it must stay on loopback. Backups: `.backup`/`VACUUM INTO`, never `cp`/`tar` on a live SQLite file. |
| **CI & publishing** | `.github/workflows/ci.yml`, `publish.yml`, `.github/dependabot.yml` | `publish.yml` reuses `ci.yml` (`workflow_call`), so an image can only be built from a commit that passed. The build carries a provenance **and** SBOM attestation (`sbom: true`). Dependabot groups minor+patch per ecosystem; majors arrive alone on purpose. |
| **Tests** | `backend/test/*.test.ts` (run by `npm test`), `backend/test/*.e2e.sh`, `frontend` `vue-tsc` | Backend tests are plain `tsx` scripts against fixtures, no runner. They log a lot of Prisma query noise; the last line (`N passed, M failed`) is the result. Frontend CI is type-check + build; there is no unit-test runner. |

## If you are looking for something and it is not here

`grep -rn "<symbol>" backend/src frontend/src` is faster than guessing at the architecture. The
route table is `backend/src/app.ts`; the frontend entry point is `frontend/src/main.ts`.
